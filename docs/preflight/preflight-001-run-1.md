## What was reviewed

What the product is for was read from `docs/project-charter.md` and `docs/releases/001-glanceable-agent-status.md`, not taken from the developer: a small always-visible surface that mirrors what every live coding-agent session is doing, agent-agnostic by construction, entirely local, negligible footprint. Its stated non-goals are controlling or messaging an agent, being a log or transcript viewer, and virtual-pet game mechanics.

What the release changed was read from the release scope's Planned Work and Explicit Scope Changes, the six story specs in `docs/stories/`, the design doc, `docs/backlog.md`, and the full commit history — release 001 is the project's first release, so every one of the 51 commits from `578439d` to `7f20b60` belongs to it and the tree *is* the release. The release's own status is `Implementing`: C-028 is `Scoped` and unbuilt, and story 007's spec round has already rejected C-014. This receipt is therefore evidence about a release still in flight, not about a finished one.

The unit reviewed: `core/` (Rust observation core, 8 modules), `macos/Sources/` (Swift AppKit surface, 3 modules), `build.sh`, `test.sh`, `macos/Package.swift`, `core/Cargo.toml`, `README.md`, and the fixtures under `core/fixtures/codex/`. Both suites were run rather than read: `cargo test` — 137 passed, 0 failed; `swift test` — 47 passed, 0 failed.

## Surface covered

This product is a read-only local observer with a drawn window on top of it, so what it can actually fail at is narrow and specific:

- **Reading another program's private files correctly** — liveness proof, status mapping, timestamp parsing, tailing files that are being appended to while they are read, and behaviour when any of that is malformed, truncated, mid-write, or from a version of the agent nobody has seen. This is where nearly all of the product's risk lives, and it is where the review spent most of its time.
- **The adapter seam** — the release's own criterion is that adding Codex required no change to the pet, so whether agent knowledge has leaked out of the adapters is a thing this product can fail at in a way that matters.
- **Saying something false on a glanceable surface** — the release's stated goal is a glance that can be trusted, so a row that states an age, a state, or an activity that is not true is a correctness failure here, not a cosmetic one.
- **Not being noticed** — the charter constrains CPU and battery, and the surface's whole value is that it can be left running.
- **What the release's own records claim about the code** — the project decides scope from written rationales, so a rationale that misstates the code is a defect in the release, not a documentation nicety.

## Ruled out

- **Network, transport and data-in-transit security** — nothing crosses a process boundary except the FFI string between the Rust core and the Swift surface in the same address space. No sockets, no HTTP client, no telemetry; verified by the absence of any networking dependency (`core/Cargo.toml` has exactly two: `serde`, `serde_json`).
- **Authentication, authorisation, tenancy and secret handling** — one user, one machine, no accounts, no credentials read or stored anywhere in the tree.
- **Persistence, migrations and data loss** — the product owns two pieces of state, both trivially rebuildable: `~/.config/agent-pet/config.json` (hand-written, read-only to the app) and four `UserDefaults` keys of window geometry. Nothing the pet writes can lose anything.
- **Writes to agent-owned files** — ruled out as a *risk*, confirmed as a *property*: every filesystem call in `core/` is `File::open`, `read_to_string`, `read_dir` or `metadata`; there is no write, create, remove or rename outside `#[cfg(test)]` code.
- **Concurrency and data races** — the core is a single `Mutex<Observer>` polled from one thread; the surface is main-thread AppKit. No shared mutable state crosses a thread.
- **Cross-platform behaviour** — macOS only, by the release's own targeting, and the `ps`/`lsof`/AppKit dependencies are stated as such.
- **Accessibility and internationalisation** — outside the release's stated scope and never claimed.

Already recorded on `docs/backlog.md`, met during the review and deliberately not reported as findings:

- **C-028** — `Observer::pin_unchanged_states` (`core/src/lib.rs:124`) discards an agent's newer `status_since` whenever the displayed state is unchanged, so a turn boundary crossed between two polls leaves the row counting from the previous turn. Scoped to this release, unbuilt; the story-006 spec records the limit rather than hiding it.
- **C-022** — the creature in `CreatureView.swift` is a placeholder, and its working face reads as unhappy.
- **C-023** — the click-through cache in `PetController.updateClickThrough` has to be invalidated by every mover of the surface.
- **C-026** — the bubble's side flip is instant rather than animated.
- **C-021**, **C-018**, **C-015**, **C-027** — bubble click targets, per-agent icons, persisted learned profile directories, and time-since-last-activity as its own signal.

## Findings

1. **Five declarations in the core are unreachable, and one of them is a second, unread source of a fact the rows already carry** — reduction · `core/src/adapter.rs:18`, `core/src/session.rs:33`, `core/src/claude/transcript.rs:126`, `core/src/claude/registry.rs:19`, `core/src/claude/mod.rs:697`
   `Adapter::agent_id()` is declared on the trait and implemented by both adapters, and nothing anywhere calls it — a grep for `agent_id()` across `core/` returns no call site. Each adapter instead stamps its id directly onto every row (`agent_id: "claude".into()` at `claude/mod.rs:195`, `agent_id: COMMAND.into()` at `codex/mod.rs:96`). `State::wants_attention` (`session.rs:33`) has no caller; the surface uses its own `SessionState.wantsAttention` in `PetState/SessionState.swift:28`. `Tailer::forget` (`transcript.rs:126`) has no caller and no test — the test named `forgetting_a_rollout_drops_what_was_remembered_about_it` exercises `retain_only` on the *Codex* tailer, which has no `forget`. `RegistryEntry.name` (`registry.rs:19`) is parsed from every registry file and never read. And `claude/mod.rs:697-699` carries an `#[allow(dead_code)] fn _unused(_: HashMap<u32, String>)` whose stated purpose is to silence the warning for a `use std::collections::HashMap` import in the same test module that nothing else uses.
   Cost: `agent_id()` is the one that costs something beyond its own lines. It is derivable state — the same fact the row already carries — held in a second place that no reader consults, so the next adapter can implement it inconsistently with what it stamps on its rows and nothing will fail. The remaining four are dead weight on the file every future adapter author is told to read as the contract, and the `_unused` stub is dead code whose entire job is to hide a symptom that deleting the import would remove.
   Verdict: Confirmed

2. **The README contradicts the shipped product in three places, one of them an instruction the user would act on** — quality · `README.md:77`, `README.md:12`, `README.md:9-53`
   `README.md:77` reads "The pet has no dock icon and no menu bar. Quit it with `pkill AgentPet`." `MenuBar.swift` builds an `NSStatusItem` with a pawprint icon, a Hide/Show Pet item and a Quit Agent Pet item bound to `NSApp.terminate`, wired in `PetController.start` at line 103; that menu bar item is C-016, added mid-release *because* an accessory app with no visible way to quit left only `pkill`, and the release scope records it as a conscious expansion that delayed the release. `README.md:12` says a row shows "how many seconds ago that was observed" — story 006 and C-017 changed exactly that: `AgentSession.status_since` is now the agent's own record of when the status began (`session.rs:59-68`), and first-seen is the fallback, not the meaning. The "What it shows" section (lines 9-53) describes rows, dots and breathing and never mentions the creature at all, though story 005 shipped a drawn creature with six expressions plus an aggregate rule (`CreatureView.swift`, `SessionState.byUrgency`) — the charter's central noun is absent from the product's only user-facing document.
   Cost: the quit instruction is wrong in the direction that costs work — it tells the user to `pkill` a process that has had a Quit menu item since story 002, which is the affordance C-016 delayed the release to add. The age sentence restates the false meaning the release added C-017 to remove, in the one document a reader consults before the code. All three are the release's own shipped behaviour, not future work, so nothing on the backlog covers them.
   Verdict: Confirmed

3. **The recorded reason for dropping C-014 is factually wrong about the Codex adapter, and the gap it was raised for is still open for Codex** — quality · `docs/backlog.md` (C-014 row), `docs/releases/001-glanceable-agent-status.md:164-177`, `core/src/codex/mod.rs:73`
   Both records state that "`core/src/codex/mod.rs` takes the directory list and never reads it, discovering by open rollout handle instead", and the release concludes from that pair of legs that "a hand-added directory can only ever matter for a session that is not running". The Codex adapter does read the list: `codex/mod.rs:73` rejects every candidate rollout that fails `under_any(path, profiles)`, `under_any` is defined at line 120 precisely to "keep discovery to the configured surface", and `codex/mod.rs:284` is a test named `a_rollout_outside_every_watched_directory_is_left_alone` asserting the resulting empty row set. The list Codex is filtered against comes from `config::default_directories()` (`~/.claude`, `~/.codex`) plus the hand-edited config plus `procs.claude_profile_dirs()` — and that last source reads `CLAUDE_CONFIG_DIR` only (`procs.rs:57-73`), so nothing learns a Codex profile directory from a live process the way it does for Claude. A running Codex CLI session under a non-default `CODEX_HOME` is therefore filtered out with no row, and the only remedy in the shipped product is hand-editing `~/.config/agent-pet/config.json` — which is the exact irritation C-014 was raised to remove.
   Cost: a committed release item was retired on a rationale that is wrong on one of its two legs, and the release scope now carries that wrong statement as the permanent record of the decision. The first leg (Claude auto-learns its profile directory, so C-014's original motivating case is genuinely covered) does hold, so this is not an argument that C-014 should have been kept — it is that the record does not support what it concludes, and the residual Codex case it dismisses is real. The practical exposure is narrow: it needs `CODEX_HOME` set away from the default, which is not the case on this machine.
   Verdict: Confirmed

4. **An agent's name has leaked out of the adapters into the shared process trait, two methods below a doc comment promising it has not** — architecture & fit · `core/src/procs.rs:23`, `core/src/profiles.rs:30`
   `ProcessTable::pids_of_command` carries the project's own statement of the rule: "Deliberately neutral: the caller names the command, so no agent's name enters this trait." Fourteen lines above it, `ProcessTable::claude_profile_dirs` names one — in the method, in its doc, and in its implementation, which greps for `claude` processes and reads `CLAUDE_CONFIG_DIR` out of each (`procs.rs:57-73`, `164-190`). It is consumed not by the Claude adapter but by pet-level code, `profiles::candidate_directories` at `profiles.rs:30`, so the directory-learning mechanism sits outside the seam every other piece of agent knowledge was deliberately pushed inside — including liveness, which `adapter.rs:12-16` records as having been moved into the adapters for exactly this reason.
   Cost: the mechanism cannot be reused by a second agent without adding a second pet-level method and a second call in `profiles.rs`, which is the change the release promises adding an agent does not require; and it is why finding 3's Codex gap exists at all, since the neutral version of this method would have closed it for free. Plausible rather than Confirmed because the release's criterion is met as literally written — adding Codex required no change to the pet, because Codex did not happen to need a learned directory — and a reasonable reader can hold that one narrowly-scoped, clearly-labelled exception in an infrastructure trait is the pragmatic call rather than a leak.
   Verdict: Plausible

5. **Claude transcripts are read whole on first sight while Codex rollouts are windowed, on a size assumption the code states and does not enforce** — quality · `core/src/claude/transcript.rs:86`, `core/src/codex/rollout.rs:8-20`
   `claude::transcript::Tailer::scan` starts an unseen transcript at `offset = 0` and `read_to_end`s the whole file into memory before parsing every line. `codex::rollout` opens with a comment naming this and treating it as settled: "Story 001 reads a Claude transcript from offset 0, which is safe at its ~102 KB. A Codex rollout on this disk is 74 MB and a single-turn session reached 1.3 MB, so reading one whole would stall a poll for seconds at pet startup" — and then builds `FIRST_READ_WINDOW`, `MAX_BACKSCAN` and a chunked backscan so the Codex side never does it. The Claude side has no window, no cap, and no test covering an oversized transcript, while `codex/rollout.rs` has four. The 102 KB figure is this repository's own transcript at the time story 001 was written; nothing in the code bounds it, and the poll runs synchronously on the main run loop (`PetController.start:109`), so the read happens on the thread drawing the surface.
   Cost: the pet stalls for as long as the largest transcript takes to read and parse, once per session first seen — at startup, that is every live Claude session at once. The asymmetry is the concrete part: one adapter treats "read the whole file" as unacceptable and engineers three constants against it, the other does it, and the reason recorded for the difference is a measurement of one file rather than a bound. Plausible rather than Confirmed because no oversized Claude transcript was observed on this machine during the review, and the release's "CPU and battery impact are not noticeable" measure is the developer's stated test for whether this class of cost needs work at all — a reasonable reader can hold that a one-off read at startup is not what that measure is about.
   Verdict: Plausible

## Known gaps

None of the findings above needs capability that does not exist; each is fixable in place before the release ships.

The release does ship with a gap it recorded for itself, met and confirmed by this review rather than newly found: **Codex attention states do not exist**. `codex::rollout::boundary_state` reads only `task_started` and `task_complete`, so `CodexAdapter` can produce `Working`, `Idle` or `Unknown` and never `Waiting` or `Errored` — which means the release criterion "a waiting-for-input session and an errored session are each tellable from a working session at a glance" is met for Claude and not for Codex. The scope document records this as an explicit scope change with the spike evidence behind it, and the README states it plainly at lines 133-142. It is on the receipt because a reader of the receipt should not have to go looking for it, not because it is unrecorded.
